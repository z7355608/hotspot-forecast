**整体判断**：对**已下定决心、在选时机**的用户，本页是合格的转化漏斗。对**犹豫期用户**（占大多数），转化阻力主要来自三块：
1. 推荐黑盒 → 不信任
2. 付费预期不透明 → 不敢点
3. 个性化感知弱 → 觉得"这个工具不懂我"

## 一、当前展示能不能让用户付费？

### 1.1 用户来这页的真实诉求

按 user persona 拆解，访问这页的用户分三类：

| 用户类型 | 占比估计 | 真实诉求 | 离付费的距离 |
|---|---|---|---|
| **抄作业型**（新手起号者） | ~50% | 给我一条能直接抄的爆款 + 怎么改 | 近：愿为「跟着做就能爆」付费 |
| **找灵感型**（已稳定但缺主题） | ~30% | 给我看现在大家都在做什么、什么趋势 | 中：愿为「省我刷半小时同行」付费 |
| **学方法论型**（运营 / MCN） | ~20% | 给我看爆款的底层逻辑、可迁移的公式 | 远：要看深度内容才付费 |

**当前页对 3 类用户的命中度**：

- **抄作业型**：✅ 强 — 4 张高分卡 + 标题模版 + 深度拆解 = 完整可抄链路。
- **找灵感型**：⚠️ 中 — 7 日趋势榜命中诉求，但只展示 7 条且没有"切赛道"的快速过滤。
- **学方法论型**：⚠️ 中 — DB 速览的「爆款原因」太短，深度拆解才解渴，但要付费 → 卡在转化前。

### 1.2 现在的页面会让"抄作业型"用户付费吗？

**会的关键链路**（理想路径）：
```
看到 4 张卡 → 看到 80%+ 爆款分 → 好奇 → 点卡 → 看到 DB 速览 → 不够具体
→ 点「深度拆解」 → 触发 LLM → 付费/扣点 → 拿到 25 分镜 → 复刻 → 真的爆了 → 复购
```

**会失败的链路**（现实流失）：
```
看到 4 张卡 → "凭什么这几个？" → 怀疑 → 点了一张 → DB 速览像广告词 → 不再点深度拆解 → 走人
            ↑
    流失点 1：推荐不透明
                                ↑
                       流失点 2：DB 速览价值感不足
                                                ↑
                              流失点 3：不知道点深度拆解会不会扣费/扣多少
```

### 1.3 三个核心流失点的证据

#### 流失点 1：推荐黑盒

代码现状（`server/routers/low-follower.ts:144`）：
```sql
ORDER BY is_strict_hit DESC, viral_score DESC
LIMIT ? OFFSET ?
```
前端用户看到的：4 张卡 + 一个分数百分比 + "默认热度 / 赛道专属" 标签。

用户视角的疑问：
- viral_score 是怎么算的？是平台数据还是你们自己造的？
- 为什么不是上周的爆款？为什么不是我关注的赛道？
- 同分情况下为什么是这条不是那条？

**症结**：分数本身没问题（`viral_score` 在 `low-follower-algorithm.test.ts` 里有完整算法），但用户感受不到这是个"靠谱算法"，会下意识当成"运营随便挑的"。

#### 流失点 2：DB 速览像广告词

代码现状（`HotTopicRecommendationsPage.tsx` 的 `aiReasons`）：
```ts
if (featured.burstReasons.length > 0) return featured.burstReasons.slice(0, 3);
if (featured.suggestion) return [featured.suggestion];
```
`burst_reasons` 是建库阶段批量打的标签，文本短、套路化。

用户视角：看到「悬念开头 + 强反转 + 情绪共鸣」这种 3 句话，能感觉到模板化，**没有"为我"的成分**——任何爆款都能套用，等于没说。

#### 流失点 3：付费预期不透明

代码现状：「深度拆解」按钮没有任何文案告诉用户会发生什么。用户大概率有一个心理：
- "点下去会不会扣点数？扣多少？"
- "我今天还能免费用几次？"
- "如果我点了不满意，能退吗？"

而 `server/routers/copywriting.ts` 用的是 `protectedProcedure`，意味着确实需要登录态——但页面没暴露任何配额信息。

#### 这三个点在本轮已经做了什么 vs 还没做

| 流失点 | 本轮已做 | 还差什么 |
|---|---|---|
| 黑盒 | 顶部加了"近 14 天 · 榜单更新于 X" | 缺：每张卡的「为什么推荐你」一句话理由 |
| 速览价值感弱 | 标签从「AI 实时」改为「DB 速览 / 归集」，预期管理诚实 | 缺：用 LLM 给每个 featured 生成"个性化一句话"（贵但值得） |
| 付费预期 | 缓存让重复点击不扣费 | 缺：UI 上显式"还剩 N 次免费 / 此动作消耗 X 点" |

### 1.4 结论

**当前转化率结构**（粗估）：
- 进页率：100%
- 点任意卡：~60%（卡片够吸引）
- 点深度拆解：~15%（流失点 1+2）
- 实际付费/续费动作：~5%（流失点 3）

**改 3 个点能把"点深度拆解"率从 15% 拉到 30%+**——这是本文最后给的优先级建议。

## 二、为什么推荐这几个？合理吗？

### 2.1 推荐的真实算法

接口：`trpc.lowFollower.list`（`server/routers/low-follower.ts:58`）

**默认规则**（用户没做赛道画像）：
```sql
WHERE platform_id = ?
  AND author_followers > 0
  AND (video_published_at >= NOW() - 14 DAY OR last_refreshed_at >= NOW() - 14 DAY)
ORDER BY is_strict_hit DESC, viral_score DESC
LIMIT 12
```
前端切前 4 张展示。

**赛道专属规则**（已做画像）：
- 上式再叠加 `seed_topic LIKE %用户niche%`
- 不足 4 条 → 自动用默认规则补足

### 2.2 viral_score 是怎么来的？

详见 `server/legacy/low-follower-algorithm.ts` 和 `low-follower-algorithm.test.ts`。核心思想：

```
viral_score ≈ f(
  weighted_interaction,    // (likes×1 + comments×3 + shares×5 + collects×4) / followers
  fan_efficiency_ratio,    // views / followers，「以小博大」程度
  follower_view_ratio,     // 校准粉丝量级偏置
  engagement_rate          // (likes+comments+shares+collects) / views
)
```

进一步还有 `is_strict_hit` 标记（严格命中爆款定义的样本，置顶），以及随时间衰减的 `viral_score_trend`（"new" / "rising" / "plateau"）。

**算法本身合理**——三个 ratio 维度都是公认的低粉爆款判定信号。问题不在算法本身，而在：

### 2.3 为什么"算法合理"≠"推荐最优"

1. **缺时效衰减权重**
   - 当前 SQL 排序里**没有**让"新发布的"加分。
   - 14 天窗口内，第 1 天发的和第 14 天发的优先级一样。
   - 用户视角：「这个是 13 天前的，我现在做还来得及吗？」→ 流失。

2. **缺"复刻友好度"加权**
   - DB 已有 `newbie_friendly` 字段（`rowToItem` 已映射，前端没用）。
   - 当前给所有人推 viral_score 最高的，但顶流大号做出来的爆款，普通新手是复刻不了的。
   - 建议：在 SQL 排序加 `viral_score * (newbie_friendly / 100) AS effective_score`。

3. **缺多样性打散**
   - 当前 LIMIT 12 切 4，可能 4 张全是同一作者或同一选题。
   - 用户感受：「你给我看 4 个一样的有什么用？」
   - 建议：在 SQL 后 group by author/seed_topic 去重，再取 4 张。

4. **缺"上升期"优先**
   - 已有 `viral_score_trend` 字段，但当前排序不用它。
   - "rising" 的样本对用户的复刻价值远高于 "plateau"——用户看到的是机会，不是回顾。

5. **个性化信号薄**
   - 当前个性化只看 `userEditedNiche` 和 `userStage`。
   - 没用：用户最近浏览过哪些拆解、收藏过哪些样本、付费过哪些深度分析。
   - 建议：在 `personalization.getProfile` 旁边加一个 `getRecentEngagement` 端点，把 last 30 days 的"已拆解作品"反向喂给推荐过滤器。

### 2.4 给「为什么推荐你这条」补一段 LLM 解释，值不值

代价：每张卡 1 次 LLM 短文本生成 ≈ 200-400 tokens。4 张卡 = 1600 tokens / 用户进页一次。

按当前定价（`docs/llm-budget.md` 应该有），这是个**值得花的钱**——它直接回应了流失点 1（推荐不透明）。

实施建议：
- 不在卡片上 inline 显示完整解释（会撑爆排版）
- 改为 hover 卡片或点击卡片后，在 DB 速览区追加一段「为什么推荐你这条」（≤ 50 字，LLM 一次性给）
- 缓存 reason 到 `low_follower_samples` 的扩展表，按 (videoId, userNiche) 缓存 24 小时

## 三、当前布局是最优解吗？

### 3.1 现在的布局结构

```
┌──────────────────────────────────────────────────────────────┐
│  顶部：标题 + 推荐模式标签 + 近 14 天 / 更新于 X 小字              │
├────────────────────────────────────┬──────────────────────────┤
│  4 张推荐卡（grid 2x2 / 4x1）       │  [sticky 右侧栏]            │
│  ┌─────┬─────┬─────┬─────┐         │  • 7 日趋势 (7 条)         │
│  │ 卡1 │ 卡2 │ 卡3 │ 卡4 │         │  • 实时热词 (8 个 chip)    │
│  └─────┴─────┴─────┴─────┘         │  • 平台切换 (3 个，主力/试运营) │
│                                    │                          │
│  拆解预览区 (DB 速览)                │                          │
│  ┌──────┬─────────────────┐        │                          │
│  │ 缩略图│ 标题+4 数据+原因 │标题模版 │                          │
│  └──────┴─────────────────┘        │                          │
│                                    │                          │
│  CTA 紧凑版 (3 张：预测 / 浏览 / 画像) │                          │
└────────────────────────────────────┴──────────────────────────┘
```

### 3.2 这个布局做对了什么

✅ **信息密度高**：用户一屏内能看到「啥火 + 怎么火 + 趋势 + 切平台」
✅ **决策路径清晰**：卡 → 拆解预览 → 深度拆解 是线性递进
✅ **右侧栏 sticky**：滚动时平台切换/趋势始终可见，鼓励横向探索
✅ **CTA 紧凑版收尾**：最后给行动出口，不让用户走死胡同

### 3.3 可以更好的地方（按效用排序）

#### A. 首屏加「今日机会」单卡（最高优先级）

现在用户进页面看到的第一行是 4 张卡 + 一堆数据，决策成本高。

更好的做法：在 4 张卡上方加一张通栏卡片：
```
┌─────────────────────────────────────────────────────────┐
│ 🔥 今日机会 · {基于你的 niche 和当前趋势}                  │
│                                                         │
│ 「{LLM 生成的一句话}：今天「办公室小段子」赛道 7 日均分    │
│  + 18%，「茶水间反差感」选题低粉新号还有空位 ——            │
│  下面这 4 张卡是按这个角度挑的。」                        │
│                                                         │
│ [跳到我的赛道分析] [看趋势详情]                           │
└─────────────────────────────────────────────────────────┘
```
价值：
- 直接回应「为什么是这 4 张卡」（解决流失点 1）
- 给用户「今天就要做」的紧迫感
- LLM 调用次数：用户进页 1 次（可缓存到当日，所有相同 niche 用户共用）

#### B. 卡片角标语义化（中等优先级）

当前角标只有「viral_score 百分比 + 赛道」。可加：
- 🆕「上升期」（trend === "rising"）
- 🌱「新手友好」（newbie_friendly > 80）
- ⚡「今日新增」（created_at < 24h）
- ⏰「热度回落」（trend === "plateau"，弱化色）

让用户**一眼判断**这条值不值得抄，而不是要点进拆解才知道。

#### C. 拆解预览区加「免费试用次数」（最高优先级 - 转化）

在「深度拆解」按钮旁边加一行小字：
```
今日剩余 2 次免费深度拆解 · 充值后无限次  [查看套餐]
```
- 直接解决流失点 3（付费预期不透明）
- 给犹豫用户一个"反正还免费"的安全感 + 一个"快用完了"的紧迫感
- 按月活用户成本上限可控

#### D. 标题模版区做成「标题生成器」（中长期价值）

现在是被动展示同赛道 4 个标题。改成：
```
[输入你的关键词]   [生成]
↓
AI 用「{featured 的爆款公式}」为你生成 5 个候选标题
- 标题 1
- 标题 2
- ...
```
- 这是付费转化大杀器：用户的关键词 + 你的爆款公式 = 立刻可发的标题
- LLM 调用次数：每次点生成 1 次（可对同 keyword + featured 缓存）

#### E. 趋势可点击（中等优先级 - 留存）

7 日趋势的每一行点击 → 跳到 `/low-follower-opportunities?seedTopic=X`，展示该话题下全部样本 + 子排行。
- 形成深度浏览路径，提高页面停留
- 对 "找灵感型" 用户尤其有用

#### F. 「对标账号」卡（中长期价值）

在右侧栏的「实时热词」下面加一个「对标账号 Top 5」：
- 跟你粉丝量级（userStage）相近
- 最近 14 天内有爆款的
- 同赛道
- 直接展示头像 + 昵称 + 最近爆款分

这是用户**愿意付费看的**——竞品工具（蝉妈妈、新榜）的核心付费点之一。

#### G. 跨平台对比模式（中长期愿景）

切换器现在是单选（看抖音 OR 看小红书）。改为可多选 → 同选题在多平台的爆款分对比：
```
选题「办公室小段子」
  抖音：均分 87，14 天 23 条样本，趋势 +12%
  小红书：均分 76，14 天 8 条样本，趋势 +5%
  快手：均分 71，14 天 3 条样本，趋势 -2%
```
价值：直接帮用户决策"我应该发哪个平台"——这是单一平台数据回答不了的问题，跨平台数据的核心溢价。

### 3.4 更好的版本：理想布局

```
┌──────────────────────────────────────────────────────────────┐
│  [标题 + 模式标签 + 14 天 + 更新于 X]                            │
├──────────────────────────────────────────────────────────────┤

```

## 四、如果只能再做 3 件事，做什么？

按 ROI（开发成本 vs 转化提升）排序：

### 🥇 第 1 件：拆解预览区加「免费配额可视化」

- **成本**：1 天前后端
- **转化提升**：+5~10%（直接消除流失点 3）
- **怎么做**：
  - 后端 `account-center` 或 `credits` router 增加 `getDailyQuota` 端点
  - 前端在「深度拆解」按钮旁渲染 "今日剩 N 次"
  - 0 次时按钮置灰，加 [充值 / 升级] CTA

### 🥈 第 2 件：「今日机会」首屏一句话

- **成本**：2 天（含 LLM prompt 设计 + 缓存）
- **转化提升**：+8~12%（直接消除流失点 1）
- **怎么做**：
  - 新增 `trending.dailyOpportunity` mutation：给 (platform, niche, today's trends) → LLM 生成一句话 + 1 个跳转 CTA
  - 同 niche 同日缓存（一天一次 LLM 调用 / niche，预算极低）
  - 首屏单卡渲染，背景渐变 + 醒目

### 🥉 第 3 件：推荐卡的语义角标

- **成本**：0.5 天（纯前端，DB 字段已有）
- **转化提升**：+3~5%（提升信任，降低决策成本）
- **怎么做**：
  - `viral_score_trend === "rising"` → "🆕 上升期"
  - `newbie_friendly > 80` → "🌱 新手友好"
  - `created_at < 24h` → "⚡ 24h 新增"
  - 卡片角标位置已有，加新的就行

**3 件加起来约 3.5 天工作量，预期转化漏斗"点深度拆解"率从 15% 拉到 25-30%**。

## 附录 A：2026-04-28 增补 · 数据来源优化（趋势榜）

### A.1 问题

文档原 §2.3 指出"缺上升期优先"，本来作为下一轮建议；用户提出后立刻确认这是数据来源层面的根因——"趋势"模块名实不符。

修改前的 `server/routers/trending.ts:hotTopics`：

```ts
sortKey: avgScore + nicheBoost  // 按"均分"排序，delta 只是装饰
.filter((it) => it.sampleCount >= 3)
```

**症状**：用户看到的"7 日趋势"实际是"7 日均分榜"。一个三个月前就已经在高位的话题（avgScore 90、delta 0%）会一直霸榜；一个本周新冒出来涨幅 80% 的话题（avgScore 65、delta 80%）反而排在它后面。

### A.2 改动后语义（"上升榜 v2"）

```ts
sortKey: effectiveDelta + nicheBoost  // 真按上升势头排
```

**严格质量门槛**（同时满足才能进榜）：

| 门槛 | 阈值 | 目的 |
|---|---|---|
| 当期 sampleCount | ≥ 3 | 保证当期数据稳定 |
| 当期 avgScore | ≥ 50 | 排除"30→35 涨幅大但本身没价值"的伪上升 |
| 上期 sampleCount | ≥ 2（否则按 isNew 处理） | 避免单条上期样本制造伪 delta |
| delta | > 0 OR isNew | 下降的话题不进榜 |

**噪声压平**：

- `isNew`（上期 0 样本或 < 2 条）：effectiveDelta 固定 50，新话题给中等权重
- 上期 avgScore < 20：把 delta 上限封顶 80，避免低基数放大

**niche 加权**：从 +30 减到 +15，不抢主位、仅做可见性提升。

### A.3 前端联动

`TrendRow` 的视觉层级反过来：

| 之前 | 之后 |
|---|---|
| 「爆款分」紫色加粗、delta 仅在 \|delta\|≥5 时小字显示 | 「均分」灰色辅助、delta 始终红框醒目展示（榜本来就是看上升的） |
| isNew 不展示 delta 也不打标 | isNew 显示绿色「新话题」徽标 |

标题：「7 日趋势」→「7 日上升榜」（按环比涨幅排序）；副标说明门槛。

### A.4 用户视角的转变

| 场景 | 之前 | 之后 |
|---|---|---|
| 进页第一眼 | 看到几个"早就火了"的话题，没行动感 | 看到「这个话题 +35% 涨势」、「这个话题新冒出来均分 65」，有"现在不上车就晚"的紧迫感 |
| 信任度 | 「跟我刷小红书看到的差不多」 | 「这个工具识别出了我自己没注意到的上升赛道」 |
| 付费意愿 | 弱（看到的内容公开渠道也能看到） | 中→强（"上升期 + 低粉爆款"是公开渠道难以聚合的复合信号） |

### A.5 同类问题：推荐 SQL 也有相同的"未利用 trend 字段"问题

低粉爆款表里已有字段 `viral_score_trend`（"new" / "rising" / "plateau"），但 `low-follower.ts:list` 当前的 ORDER BY 完全没用它：

```sql
ORDER BY is_strict_hit DESC, viral_score DESC  -- 高分但已 plateau 的样本会持续占榜
```

**建议下一轮做的改造**（约半天工作量）：

```sql
ORDER BY is_strict_hit DESC,
         CASE viral_score_trend
           WHEN 'rising' THEN 0
           WHEN 'new'    THEN 1
           WHEN 'plateau' THEN 2
           ELSE 3
         END,
         viral_score DESC
```

效果：4 张推荐卡里优先放"正在涨"和"新出现"的样本，把"高分但已经回落"的压后。这呼应了上升榜的逻辑，让"推荐"和"趋势"两个模块的语义统一在"机会" vs "已发生"的轴线上。

不在本轮做的原因：用户本轮重点是趋势模块，先落 1 件事比一次推 2 件事更稳。

### B.1 出乎意料的发现

按 §四 第 1 件事「配额可视化」开工时调研出**远超原计划范围的问题**：

> 也就是说不管用户是 Free 套餐（0 积分）还是 Pro 套餐（600 积分），深度拆解功能**任何人无限免费用**。

这个发现把任务从"加个 UI 标签"升级成了"商业闭环是否真的接通"的产品决策。

### B.2 选定方案：C 灰度计费 + 全面可视化

经用户确认采用 C 方案：

- **后端**：在 `viralBreakdownDirect` 加扣减逻辑
- **env 开关**：`CREDIT_DEDUCTION_ENABLED`（默认 `false`），由业务侧决定何时正式开启
- **缓存兜底**：缓存命中时**不扣**（避免用户重复点击被反复收钱，符合用户心智）
- **UI 始终显示**：余额、本次消耗、缓存命中标记 — 即便扣减未开启，也让用户感知"积分体系存在"，建立付费心智

| 文件 | 改动 |

`charge` 返回结构：
```ts

  deducted: boolean,     // 实际是否扣减（缓存命中或灰度未开 → false）
  cacheHit: boolean,     // 是否走的缓存

}
```

#### 前端

| 文件 | 改动 |
|---|---|
| `client/src/app/pages/HotTopicRecommendationsPage.tsx` | 拉 `credits.getBalance`；深度拆解按钮旁显示「剩 X 积分 · ≈ N 次」；余额 < 20 时按钮置灰、点击弹 PaywallModal；充值成功后自动跳转拆解页 |

### B.4 缓存与扣减的耦合（防双扣）

注意：缓存逻辑与扣减逻辑必须按"先查缓存 → 命中即返回 → 未命中再扣"的顺序，这点在代码里已经显式保证。

```
有 transcript？ ──否──► 查缓存
                         │
                  命中 ──┴── 未命中
                  ↓             ↓
                返回（不扣）  ENV.creditDeductionEnabled？
                              │
                       false ─┴─ true
                       ↓        ↓
                       不扣    余额检查 → deduct
                       ↓        ↓（不足 → TRPCError）
                       ↓        扣减后跑 LLM
                       ↓        ↓
                       LLM     LLM
                       ↓        ↓
                     写缓存   写缓存
```

### B.5 这意味着什么 — 商业模型层面

之前文档 §1.4 估的"实际付费/续费动作 ~5%"其实是**乐观估计**：用户压根没有付费理由，因为不付也能用。本轮做了三件事改变这个：

1. **余额可见**：UI 始终显示积分余额。即使灰度未开，用户也开始建立"我有 X 积分能做 N 件事"的心智。
2. **消耗可见**：每次拆解完成后展示「本次消耗 −20」或「缓存命中 · 免费」。让用户感受到"积分被使用 / 被节省"，强化体系存在感。
3. **环路打通（开关方式）**：业务侧只需把 `CREDIT_DEDUCTION_ENABLED=true` 上线，付费闭环立即生效。配套灰度名单（如先对新注册用户生效）时，可在 deductCreditsInternal 调用前再加 user 维度的判断，无需再改业务代码。

### B.6 上线计费的运营建议（不是技术问题但相关）

如果未来要打开 `CREDIT_DEDUCTION_ENABLED`，建议同步：

1. **公告 + 老用户补贴**：所有当前用户一次性赠送 60-100 积分（够 3-5 次深度拆解），减轻"突然要钱"的体感
2. **首次拆解免费**：在 `deductCreditsInternal` 前加 `if (user.totalSpent === 0) skipFirstCharge`，给 onboarding 留体验空间
3. **包月用户的体感保护**：Pro 套餐 600 积分 / 月 = 30 次拆解；如果用户实际用量超 30 次，提示"加购积分包" — 这也是 PaywallModal 现有逻辑能处理的
4. **配额耗尽后的降级**：余额 < 20 时不要"按钮置灰"得太冷；可以给一个"看 7 天前的缓存"的入口（现有的缓存能力天然支持，只需 UI）

### B.7 本轮已落 vs 还差什么（更新文档 §五对照表）

> 已落：余额可见、消耗可见、缓存命中可见、灰度开关、付费墙拦截
> 还差：上线扣费的运营准备（公告、新用户补贴、首次免费策略）— 这是产品/运营动作，不是技术任务
