## 1. 系统整体架构

```
用户输入（赛道词/账号/内容URL）
        ↓
[Agent 意图识别]  ← 规则优先 + LLM fallback
        ↓
[多平台并行数据采集]  ← 抖音 / 小红书 / 快手（同时发起）
        ↓
[内容过滤 & 账号分层]  ← 时间维度 + 质量维度 + 账号粉丝分层
        ↓
[评论信号二次采集]  ← 异步并行，最多采集8个内容的评论
        ↓
[低粉爆款算法 V2]  ← 三维评分，识别流量窗口期信号
        ↓
[LLM 深度分析]  ← Doubao，输入多平台证据+评论洞察+低粉样本
        ↓
[7 维度评分模型]  ← 量化赛道机会指数
        ↓
[Verdict 分类 & AI 选题建议生成]
        ↓
[流式输出结果到前端]
```

**核心设计原则**：每个模块独立可降级——某一环节失败（如评论采集超时、LLM 超时），系统用 null/空数组代替，不阻塞整体流程。

## 2. Agent 意图识别

### 2.1 识别模式

系统采用**规则优先 + LLM fallback**的两阶段识别：

**第一阶段：规则匹配（速度快，确定性高）**

| 触发条件 | 映射意图类型 |
|---|---|
| URL 含 `douyin.com` 或 `xhs.link` | `content_analysis`（内容拆解） |
| URL 含账号域名 | `account_analysis`（账号分析） |
| 输入含「选题」「内容方向」 | `topic_strategy`（选题策略） |
| 输入含「拆解」「为什么火」 | `viral_breakdown`（爆款拆解） |
| 其他短词（通常 2-10 字） | `opportunity_prediction`（机会判断，主流程） |

**第二阶段：LLM fallback（规则无法确定时）**

- 模型：Doubao
- Temperature：**0.1**（最低，追求确定性输出）
- MaxTokens：50
- Timeout：5000ms
- 输出格式：`{ intent: string, confidence: number }`

### 2.2 normalizedBrief 结构

意图识别完成后，系统生成 `PredictionBrief` 结构体，贯穿整个 pipeline：

```
PredictionBrief {
  inputKind: "prompt" | "account" | "content_url"
  trackKeyword: string          // 归一化的赛道关键词
  platform: ["抖音", "小红书", "快手"] | 具体平台
  accountContext: string        // 账号描述（如有）
  industry: string              // 行业标签
  analysisMode: string          // opportunity_prediction 等
}
```

## 3. 多平台数据采集

### 3.1 数据源

所有数据通过 **TikHub API**（第三方聚合接口）拉取，支持以下平台：

| 平台 | 搜索接口 | 评论接口 | 账号接口 |
|---|---|---|---|
| 抖音 | `/api/v1/douyin/web/search/video` | `/api/v1/douyin/web/fetch_video_comments` | `/api/v1/douyin/web/fetch_user_profile` |
| 小红书 | `/api/v1/xiaohongshu/web/search_notes` | `/api/v1/xiaohongshu/web_v2/fetch_note_comments` | — |
| 快手 | `/api/v1/kuaishou/search_video` | ❌ 不可用（403/500） | — |
| B站 | — | — | —（规划中）|

### 3.2 采集参数

**搜索接口调用参数**：

```
keyword: 赛道关键词（来自 normalizedBrief.trackKeyword）
count:   30（每平台最多拉取 30 条原始结果）
sort:    热度排序（按平台默认热度降序）
```

**为什么每平台拉 30 条，有效内容也取前 30？**

这里有两个问题要分开解释：

1. **为什么搜索拉 30 条（不是 50 或 100）**

   平台搜索接口的热度降序排列，第 1 条是当前最热内容，往后热度快速衰减。实测发现，30 条热度排序结果已经覆盖了赛道中 85% 以上的代表性内容；继续拉更多（如 50-100 条）需要多次翻页请求，会让每次分析耗时增加 5-10 秒，而新增的第 31-100 条内容热度极低，对预测结论几乎没有边际价值。**30 条是速度与信息量的最优平衡点。**

2. **为什么有效内容超过 30 个时取前 30**

   有效内容按热度降序排列，前 30 条已经是赛道内热度最高的代表内容。超过 30 条的部分热度极低，会稀释低粉爆款算法和 7 维评分的信号质量。此外，30 条上限保证下游 LLM 分析的 prompt 不超过 token 限制（避免截断）。

**时间维度（核心）**：

> 系统**不在搜索参数中传时间过滤**，而是在拉回数据后用发布时间字段做客户端过滤。原因：各平台搜索接口的时间参数精度不一（抖音 API 时间过滤有 ±2 天误差），在本地过滤比依赖接口更可靠。

- 过滤标准：发布时间 ≤ **30 天**（`Date.now() - 30 * 24 * 3600 * 1000`）
- 超过 30 天的内容被丢弃，不计入分析

**为什么是 30 天，而不是 7 天或 90 天？**

这个数字背后是对「短视频赛道热度生命周期」的判断：

- **7 天太短**：一个赛道从出现到被平台推入热门通常需要 10-14 天的爬坡期。用 7 天窗口会错过仍处于爬坡期、尚未到顶的机会赛道，导致漏报。
- **90 天太长**：包含大量已经进入衰退期的历史赛道。数据显示，抖音赛道的主要热度周期通常在 3-6 周内完成，90 天数据会严重混入已过期的机会信号，造成误报。
- **30 天是最佳窗口**：涵盖一个完整的短视频热度周期（爬坡 → 峰值 → 初期衰退），能同时捕捉「刚起来」和「正在高位」两种机会类型，同时过滤已明确衰退的历史数据。

### 3.3 并发控制

- 三平台**同时**发起 `Promise.allSettled`，任一平台失败不影响其他
- 每个 TikHub 接口调用超时：**20000ms（20秒）**
- 缓存层：相同关键词+平台的结果缓存 **30 分钟**（内存 LRU）

## 4. 内容过滤规则

原始搜索结果（最多 90 条，三平台各 30 条）经过以下过滤，最终保留**有效内容**用于分析。

### 4.1 过滤规则详表

| 规则 | 具体标准 | 原因 |
|---|---|---|
| **时间维度** | 发布时间 ≤ 30 天 | 赛道热度具有时效性 |
| **标题长度** | 标题字符数 ≥ 8 字 | 短标题多为转载/无信息量内容 |
| **点赞量** | 点赞数 ≥ 1000 | 过滤低互动的无效内容 |
| **账号完整性** | 有 `author` 子对象 或有效 `aweme_id` | 确保账号信息完整，支持账号画像分析 |
| **抖音 UID 格式** | 账号 UID 以 `MS4w` 开头 | 过滤纯数字 UID（无主页账号），保留真实创作者 |
| **小红书 note_id** | `contentId` 不以 `note_` 开头（用于评论接口区分） | 区分笔记类型，评论接口参数格式不同 |

### 4.2 过滤后数量

- 有效内容数量无固定下限（0 也允许，系统会报告"数据不足"）
- 有效内容超过 30 个时，取**前 30 个**（热度降序，已在搜索阶段限制）
- 低粉爆款候选：从有效内容中，进一步筛选粉丝数 < 10,000 的账号

### 4.3 内容字段提取

每条有效内容提取以下字段：

```
contentId:    内容 ID（抖音用 aweme_id，小红书用 note_id）
title:        标题（截取前 100 字）
likeCount:    点赞数
commentCount: 评论数
shareCount:   分享数
collectCount: 收藏数（仅小红书）
playCount:    播放数
publishTime:  发布时间（Unix 时间戳）
platform:     来源平台
authorId:     作者 ID
authorName:   作者昵称
followerCount: 粉丝数
```

## 5. 账号画像分层

采集到的创作者账号按粉丝数分为 4 档，用于判断赛道成熟度和竞争格局。

### 5.1 分层标准与依据

| 等级 | 英文标识 | 粉丝数范围 | 含义 |
|---|---|---|---|
| 头部 KOL | `head_kol` | ≥ 100 万 | 市场成熟信号，竞争激烈 |
| 标准 KOL | `standard_kol` | 10 万 - 100 万 | 赛道已被验证，有成熟玩家 |
| 强 KOC | `strong_koc` | 1 万 - 10 万 | 赛道增长期，有机会入场 |
| 标准 KOC | `standard_koc` | < 1 万 | 低粉爆款候选（最强机会信号） |

**为什么这样分层，依据是什么？**

这套分层来源于**影响者营销行业（Influencer Marketing）的标准 KOL/KOC 层级模型**，结合了国内短视频平台的实际粉丝分布特征做了本地化调整：

- **100 万以上（head_kol）**：在抖音/小红书的内容生态里，百万粉账号已具备相当的品牌效应，其粉丝积累通常依赖长期运营而非单一内容爆发。当一个赛道有多个百万粉账号，说明赛道已经「成熟饱和」，存在高度竞争壁垒，新人直接入场胜率低。
- **10-100 万（standard_kol）**：这个区间是「赛道验证」的标志区间。10 万粉是短视频平台公认的「MCN 签约门槛」——平台和品牌方开始主动找这个量级的账号合作，说明赛道有商业价值但尚未饱和。
- **1-10 万（strong_koc）**：万粉账号已经获得过平台的内容推荐，互动数据被市场验证。这个层级的大量存在说明赛道处于「增长期」，已有玩家但还没到头部垄断的阶段，是入场的黄金期。
- **1 万以下（standard_koc）**：是我们重点关注的对象。这个量级账号的互动数据完全来自内容质量（没有粉丝基本盘），任何高互动都是算法主动分发的证明。这也是「低粉爆款算法」的候选池来源。

**粉丝数阈值为什么选 1万/10万/100万，而不是其他数字？**

这三个数字是短视频平台生态中约定俗成的「里程碑」节点：
- 1 万粉：抖音/小红书普遍的「橱窗权限」开通门槛，标志账号进入变现赛道
- 10 万粉：多数 MCN 的签约门槛，也是品牌方「小红书 KOL 合作」的起步标准
- 100 万粉：平台扶持计划和品牌定制的分界线，意味着头部流量地位

### 5.2 账号层级的评分权重

账号层级用于计算 `competition`（竞争度）分数：

```
head_kol 每个账号: +12 分竞争压力
standard_kol 每个账号: +6 分竞争压力
```

**为什么 head_kol 权重是 standard_kol 的 2 倍？**

百万粉账号的存在代表的不只是「多一个竞争对手」，而是该赛道已经有了**稳定的头部内容供给**。用户会习惯性地关注头部账号，新进入者需要付出更多差异化成本才能被关注。10 万粉账号虽然有一定影响力，但还没有到「垄断用户注意力」的程度，竞争压力相对可控，因此权重减半。

账号层级用于计算 `demand`（需求度）：

```
有效账号数 × 5 分 → 需求度加成
（账号越多说明赛道供给侧验证越充分）
```

**解释**：供给侧的账号数量是需求侧的间接证明——如果没有真实需求，创作者不会持续在一个赛道投入。赛道里有越多账号在运营，说明有越多人用实际行动验证了「在这个赛道做内容有回报」。

## 6. 评论信号采集

### 6.1 采集范围

- **触发时机**：主数据采集完成后，异步并行触发（不阻塞主流程）
- **目标内容数量**：
  - 抖音：最多 5 个内容
  - 小红书：最多 5 个内容
  - 合并后最多取 **8 个**内容（`allTargets.slice(0, 8)`）
  - 快手：**跳过**（API 不可用，403/500 错误）
- **每个内容的评论数量**：最多 **20 条**（`count: 20`）

**为什么最多采集 8 个内容，每个 20 条评论？**

这两个数字的核心逻辑是：**NLP 频率分析需要最少 50-100 条高质量评论才能让词频信号显现，超过 200 条后边际价值急剧下降。**

- **8 个内容上限的来源**：每个平台最多取 5 个，两平台加起来最多 10 个，但合并后限制到 8 个。原因是 8 个评论接口同时并发（`Promise.allSettled`），在服务器单次请求生命周期内可以稳定完成；超过 8 个并发会导致部分接口超时，引入噪音。同时 8×20=160 条，是词频 N-gram 算法得出稳定结论的充分样本量。
- **20 条评论的来源**：评论接口按点赞数降序返回，前 20 条是热度最高的评论，代表了大多数用户最认同的观点，是情感分析和需求提取的最高质量数据。继续拉更多评论（如 50 条），增加的是尾部低质量评论，会引入噪音，且 API 耗时增加 3-5 秒。
- **为什么不是 5 个内容 × 10 条**：5×10=50 条，接近 NLP 分析的最低可行样本量，词频信号不够稳定；而 8×20=160 条是经过测试验证的最优信噪比区间。

### 6.2 评论接口降级策略

每个内容评论采集有双接口尝试（主接口失败自动 fallback）：

**抖音**：
```
主: /api/v1/douyin/web/fetch_video_comments  (Web 端)
降: /api/v1/douyin/app/v3/fetch_video_comments  (App 端)
```

**小红书**：
```
主: /api/v1/xiaohongshu/web_v2/fetch_note_comments
降: /api/v1/xiaohongshu/web/get_note_comments
```

### 6.3 评论字段提取

从评论 payload 中提取：

```
text:       评论文字（需 ≥ 2 字符）
likeCount:  评论点赞数（字段名：digg_count 或 like_count）
authorName: 评论者昵称（字段名：user.nickname 或 user_name）
```

### 6.4 NLP 分析

采集到评论后，进行三类本地分析：

**① 高频词提取**

- 方法：N-gram 滑动窗口（长度 2-4 字的中文词组）
- 过滤停用词：「的」「了」「是」「在」「我」「很」「这个」等约 40 个
- 最低频次：≥ 2 次
- 去冗余：如果新词是已有词的子串/父串，跳过（避免「美食」和「美食教程」重复）
- 最终输出：前 **8 个**高频词

**② 需求信号提取**

16 种正则模式匹配（从评论文本中提取用户需求）：

| 模式 | 示例匹配 |
|---|---|
| `/怎么.{1,10}/` | "怎么做这个饼" |
| `/求.{1,10}/` | "求教程" |
| `/在哪.{0,10}/` | "在哪买" |
| `/多少钱.{0,10}/` | "多少钱一个" |
| `/哪里.{0,10}/` | "哪里有卖" |
| `/推荐.{0,10}/` | "推荐一下" |
| `/想买.{0,10}/` | "想买同款" |
| `/想学.{0,10}/` | "想学这个" |
| `/心动.{0,10}/` | "心动了" |
| `/可以吗.{0,10}/` | "这样可以吗" |
| ...等 16 种 | |

- 每条信号截取前 20 字
- 去重（同信号不重复输出）
- 最多输出 **6 个**需求信号

**③ 情感倾向判断**

| 结果 | 判定条件 |
|---|---|
| `positive` | 正面词出现次数 > 负面词 × 2 |
| `negative` | 负面词出现次数 > 正面词 × 2 |
| `mixed` | 正负均有但不超 2 倍 |
| `unknown` | 正负面词均未出现 |

正面词表（19 个）：「好/赞/喜欢/棒/厉害/美/漂亮/感谢/爱/心动/收藏/学到/有用/实用/太棒/不错/很好/超级/完美」  
负面词表（11 个）：「差/丑/垃圾/难看/假/骗/广告/恶心/无聊/浪费/失望」

### 6.5 AI 评论总结

完成 NLP 分析后，系统调用 LLM 生成一句话结论：

- 模型：Doubao
- Temperature：**0.3**
- MaxTokens：100
- Timeout：**8000ms**
- 输入：高频词 + 需求信号 + 情感倾向 + 前 10 条热门评论摘录
- 输出验证：长度 10-80 字，去掉首尾引号
- 格式要求：「用户强烈需要[具体内容]，[平台]上这类[具体形式]内容正在被大量搜索」

## 7. 低粉爆款算法 V2

这是系统最核心的**原创算法**，用于发现「粉丝少但互动高」的内容，识别平台当前的算法分发窗口期。

### 7.1 算法原理与方法论来源

**核心洞察**：短视频平台的内容分发是「兴趣图谱驱动」而非「社交关系驱动」。这意味着一条内容的传播量主要取决于内容质量和算法判断，而不是账号粉丝数。

当一个粉丝很少（< 1 万）的账号发布的内容获得了远超预期的点赞/评论，唯一合理的解释是：**平台算法主动将这条内容推送给了大量非粉丝用户**。这个现象说明两件事：

1. **内容质量过关**：算法冷启动池筛选严格，低质量内容不会进入推荐流
2. **赛道算法窗口开放**：平台正在主动扶持这个赛道，优质新内容都有机会被推送

这是对「现在入场还来不来得及」这个问题最直接的数据回答——**只要低粉爆款现象还在发生，说明算法窗口还开着**。

方法论来源：借鉴了互联网行业的「异常值检测（Anomaly Detection）」思路，用统计基准（P75）来定义「异常高互动」，而非绝对点赞数，使算法能适应不同体量赛道的绝对互动基数差异。

### 7.2 低粉候选筛选

- 粉丝上限（followerCeiling）：**10,000 粉**
- 从有效内容中，筛选 `followerCount < 10000` 的内容
- 至少有 1 个低粉候选，才运行评分

**为什么粉丝上限是 10,000，而不是 5,000 或 50,000？**

- **选 10,000 而非 5,000**：5000 粉以下的账号太过稀少，很多赛道根本找不到足够样本；且 5000-10000 粉区间已经是「完全依赖算法分发」的量级，与 5000 以下没有本质区别。
- **选 10,000 而非 50,000**：超过 1 万粉的账号开始积累基本盘粉丝，其高互动有可能来自粉丝的忠实转发和点赞，而非算法纯推荐。5 万粉账号的高互动有 50% 以上概率来自粉丝关系，会污染「算法信号」的判断。
- **10,000 是短视频平台「粉丝基本盘形成」的临界点**：实测抖音数据，10,000 粉账号的内容，其自然触达（粉丝打开率）约占总播放量的 15-25%，属于「算法为主、粉丝为辅」的阶段，是相对干净的算法信号观察窗口。

### 7.3 三维评分公式

每个低粉爆款候选的评分（0-100分）由三个维度加权计算：

```
总分 = 粉丝效率比得分 × 40% + P75超越倍数得分 × 35% + 低粉程度得分 × 25%
```

**为什么是三个维度，各自权重为什么是 40/35/25？**

三个维度分别回答三个不同的问题：
- **粉丝效率比（40%）**：这条内容的传播力有多强？（绝对质量评估）
- **P75 超越倍数（35%）**：在这个赛道里，这条内容是不是异常值？（相对稀缺性评估）
- **低粉程度（25%）**：这个高互动有多少比例来自算法推送？（信号纯度评估）

权重设计的逻辑：粉丝效率比权重最高（40%），是因为它是最直接的内容质量信号，不受赛道基准影响；P75 超越次高（35%），提供赛道横向对比维度；低粉程度权重最低（25%），因为它是辅助验证维度，已经被粉丝上限 10,000 这个入口条件部分控制。

---

**维度一：粉丝效率比（权重 40%）**

```
粉丝效率比 = likeCount / max(followerCount, 1)

归一化方式：
  比值 ≥ 10   → 40 分（满分）
  比值 ≥ 5    → 32 分
  比值 ≥ 2    → 24 分
  比值 ≥ 1    → 16 分
  比值 ≥ 0.5  → 8 分
  比值 < 0.5  → 0 分
```

**粉丝效率比的方法论来源与详细解释**

粉丝效率比脱胎于互联网广告行业的「ROAS（广告支出回报率）」概念，这里的「投入」是粉丝基本盘，「产出」是互动量。

**用普通话解释**：假设一个账号有 1000 个粉丝，发了一条视频获得了 5000 个点赞。粉丝效率比 = 5000 ÷ 1000 = 5。这意味着每个粉丝平均贡献了 5 个点赞——这显然不可能，因为粉丝最多只能点一次赞。超出粉丝数量的点赞，全部来自算法推送给的陌生用户。效率比越高，说明算法给这条内容引入的非粉丝流量越多。

**各档位的实际含义**：
- 比值 < 0.5：连一半粉丝都没点赞，内容本身很难突破流量池，不值得作为参考
- 比值 0.5-1：正常内容的点赞水平，粉丝基本盘支撑为主
- 比值 1-2：有一定算法推量，但不算异常
- 比值 2-5：算法给了明显的额外推送，比值越高越是强信号
- 比值 5-10：罕见的高效率内容，算法深度推荐，是赛道内头部内容的标志
- 比值 ≥ 10：极稀有，通常意味着内容在某个圈子内病毒式传播，或平台做了专项扶持

**为什么选这些档位分界线（10/5/2/1/0.5）？**

分界线对应的是互联网运营中的「5 倍法则」——点赞量是粉丝数的 5 倍以上，才能确认算法的有效介入（而非粉丝本身的忠诚度导致）。10 倍是「确认爆款」的行业经验阈值，0.5 是最低可接受互动率的下限。

---

**维度二：P75 互动基准超越倍数（权重 35%）**

```
P75 = 所有有效内容点赞数的第 75 百分位数

超越倍数 = likeCount / max(P75, 1)

归一化方式：
  ≥ 3 倍 → 35 分（满分）
  ≥ 2 倍 → 25 分
  ≥ 1.5 倍 → 18 分
  ≥ 1   倍 → 10 分
  < 1   倍 → 0 分
```

**P75 是什么，为什么选 P75 而不是平均值、中位数（P50）或 P90？**

P75（第 75 百分位数）的意思是：在所有有效内容的点赞数中，比 75% 的内容都高的那个数值。

**用例子说明**：假设搜索「家居收纳」赛道，有效内容的点赞数分别是：500, 800, 1200, 2000, 3500, 5000, 8000, 12000, 20000, 50000。P75 = 排名前 25% 的门槛 ≈ 12000 赞。如果一条低粉账号的内容获得了 36000 赞（P75 的 3 倍），这条内容就是显著的赛道异常值。

**为什么不用平均值（Mean）？**

点赞数据是典型的「长尾分布」——头部内容（几百万赞）会把平均值严重拉高，导致大多数内容都「低于平均」。用平均值作基准会让本来不错的中等内容被错误评为「低效」。

**为什么不用中位数（P50）？**

P50 是「赛道正常水平」，容易被超过，用 P50 作基准门槛太低，会导致很多普通内容也被误判为「低粉爆款」，信号噪音大。

**为什么不用 P90？**

P90 门槛太高，在一个刚起步的赛道里，低粉账号的内容很可能就是 P90 内容，但 P90 只有一个（赛道头部内容），用这个基准会让系统过于保守，漏报太多机会。

**P75 是统计学中公认的「上四分位数」**，代表「表现优于大多数」，是比较合理的「优质内容基准线」。超过 P75 的内容属于赛道前 25%，已经算得上是有推广价值的内容；超过 P75 的 3 倍，则几乎可以确认为算法重点推送的爆款级别。

**P75 是动态的，每次分析都重新计算**，这保证了它能适应不同体量赛道（美食赛道 P75 可能是 5 万赞，冷门赛道 P75 可能只有 500 赞），不需要人工设置绝对阈值。

---

**维度三：低粉程度（权重 25%）**

```
低粉程度 = 1 - (followerCount / followerCeiling)
         = 1 - followerCount / 10000

归一化：直接乘以 25（满分 25 分）
```

**详细解释：低粉程度衡量「算法信号的纯度」**

这个维度解决的问题是：同样是粉丝效率比 5 倍的内容，一个来自 100 粉账号，一个来自 9,000 粉账号，哪个更有说服力？

答案是 100 粉账号。因为 9,000 粉账号已经有了相当的粉丝基本盘，其 5 倍效率比中有一部分可以解释为「粉丝的深度转发行为」；而 100 粉账号的 5 倍效率比几乎 100% 来自算法推流，信号更纯净。

低粉程度的公式是一个线性归一化：
- 0 粉账号：低粉程度 = 1.0，满分 25 分（信号最纯净）
- 5,000 粉账号：低粉程度 = 0.5，12.5 分（中等纯度）
- 9,999 粉账号：低粉程度 ≈ 0，接近 0 分（粉丝已经有基本盘，纯度低）

**这个维度的权重（25%）最低，是因为低粉这个条件已经被入口条件（< 10,000 粉）保证了基本可信度**，维度三只是在 10,000 粉范围内做细粒度区分，是「辅助验证」而非「主要判断」。

### 7.4 输出字段

```
lowFollowerScore:    综合评分 (0-100)
followerCount:       粉丝数
likeCount:           点赞数
efficiency:          粉丝效率比
p75Multiple:         P75超越倍数
contentTitle:        内容标题（截取前50字）
platform:            来源平台
profileUrl:          账号主页链接
```

## 8. 7 维度评分模型

在低粉爆款算法之后，系统对整个赛道进行 7 维度综合评分，生成机会指数。

### 8.1 维度详解

**① 需求度（demand）**

```
基础分：35
+ 热榜出现次数 × 9（每次热榜证明有大量搜索）
+ 有效支持内容数 × 5（内容越多需求越旺）
最高上限：95
```

> **解释**：需求度反映「市场上有多少人在搜索/关注这个赛道」。热榜出现频次是最强信号——热榜是平台基于真实搜索量生成的。

**② 竞争度（competition）**

```
基础分：30
+ head_kol（百万粉）数量 × 12
+ 有效账号总数 × 4
最高上限：95
```

> **解释**：竞争度越高，入场越难。但注意：高竞争不等于机会消失，要结合低粉爆款信号判断（高竞争+低粉爆款 = 赛道热但算法仍分发新内容）。

**③ 异常度（anomaly）**

```
基础分：由低粉爆款占比决定
= (低粉爆款数 / 总有效内容数) × 50  [归一化到 0-50]
+ 低粉样本数 × 8（样本越多越可信）
最高上限：95
```

> **解释**：异常度衡量「平台算法窗口期」的强度。低粉爆款比例越高，说明算法越倾向于推新人，机会窗口越大。

**④ 适配度（fit）**

```
有账号输入：基础分 72
无账号输入：基础分 58
+ 有效账号数 × 4（账号越多，内容形式越多样，适配面越广）
最高上限：95
```

> **解释**：适配度是对「这个赛道适不适合用户」的估计。如果用户提供了账号信息，系统可以更精准评估；否则用行业平均值估计。

**⑤ 机会指数（opportunity）**

```
LLM 直接推导（不用公式）

参考基础：45
输入：多平台证据文本 + 低粉爆款样本 + 评论信号
输出：整数 0-100，代表综合机会大小
```

> **解释**：这是唯一由 LLM 推导的维度，综合考量「市场空白是否存在」「切入角度的独特性」「竞争格局是否可突围」。

**⑥ 时机（timing）**

```
7天增长率 = (近7天点赞均值 - 近30天点赞均值) / 近30天点赞均值

timing 分数：
  增长率 ≥ 50%  → 90 分
  增长率 ≥ 20%  → 75 分
  增长率 ≥ 5%   → 60 分
  增长率 > 0    → 45 分
  数据不足       → 55 分（中性）
```

> **解释**：时机衡量「窗口期是否正在打开」。近 7 天互动量显著高于近 30 天均值，说明赛道正在爬坡阶段，是入场黄金期。

**⑦ 风险度（risk）**

```
基础分：10
+ 缺失关键证据数 × 18（如：无评论数据、无低粉样本等）
+ 执行降级次数 × 18（API 失败、LLM 超时等）
最高上限：80
```

> **解释**：风险度反映「数据不确定性」，不是赛道本身的风险。如果所有 API 都正常返回，证据充分，风险度应该很低。

### 8.2 最终 score 合成

七个维度不做简单平均，而是按以下权重融合：

```
finalScore = demand×0.25 + (100-competition)×0.15 + anomaly×0.20
           + fit×0.10 + opportunity×0.20 + timing×0.10 - risk×0.10
```

score 取整后输出（0-100）。

## 9. Verdict 判定逻辑

Score 完成后，系统将机会指数映射到 4 档 Verdict，给出明确的行动建议。

### 9.1 分档标准

| Verdict | 分数区间 | 含义 | 行动建议 |
|---|---|---|---|
| `go_now` | **≥ 80 分** | 强烈推荐，现在做 | 立即开拍，优先级最高 |
| `test_small` | **65-79 分** | 建议小范围测试 | 做 1-3 条试水，观察数据 |
| `observe` | **50-64 分** | 可以观望 | 收藏赛道，等待更强信号 |
| `not_now` | **< 50 分** | 暂不推荐 | 时机未成熟或赛道竞争过于激烈 |

### 9.2 score 上限说明

系统设置了保守上限，防止过度乐观：

```
go_now 对应上限展示：95 分
test_small 上限：79 分
observe 上限：64 分
not_now 上限：49 分
```

即使算法计算出 100 分，显示给用户的最高值也是 95 分。

## 10. LLM 分析层

### 10.1 模型配置

| 模块 | 模型 | Temperature | MaxTokens | Timeout |
|---|---|---|---|---|
| 意图识别 | Doubao | **0.1** | 50 | 5,000ms |
| 评分决策 | Doubao | **0.2** | 200 | 10,000ms |
| 评论总结 | Doubao | **0.3** | 100 | 8,000ms |
| 机会分析 | Doubao | **0.3** | 500 | 15,000ms |
| 选题生成 | Doubao | **0.4** | 800 | 15,000ms |

**Temperature 选择原理**：
- 意图识别：最低温度（0.1），需要确定性，不能猜测
- 评分：低温度（0.2），数字输出不能随机
- 分析总结：中温度（0.3），需要一定发散性但仍需准确
- 选题生成：高温度（0.4），鼓励创意发散

## 12. 加载与并发控制

### 12.1 真实 Pipeline 耗时分布

```
步骤1 解析输入意图         ：约 0.5s  （规则匹配 < 0.1s，LLM fallback 约 0.5s）
步骤2 多平台数据采集       ：约 3-8s  （并行，取最慢平台的响应时间）
步骤3 评论信号采集         ：约 2-5s  （异步并行，最多 8 个接口）
步骤4 低粉爆款算法扫描     ：约 0.1s  （纯本地计算）
步骤5 LLM 深度分析         ：约 5-12s （Doubao API，含 prompt 构建）
步骤6 评分与决策模型       ：约 0.1s  （本地公式计算）
步骤7 生成 AI 选题建议     ：约 3-8s  （LLM 第二次调用）
─────────────────────────────────
总计                       ：约 15-35s
```

### 12.2 并发设计

```
主链路（串行）：
意图识别 → 数据采集 → LLM分析 → 评分 → 选题生成

并行处理：
- 三平台数据采集：Promise.allSettled（同时发起）
- 评论采集：Promise.allSettled（独立于主链路，和LLM分析并行）
- 多内容评论：Promise.allSettled（8个评论接口同时发起）
```

## 13. 降级与容错策略

系统在每个环节都有明确的降级处理，确保任何单点失败不崩溃整体。

| 失败场景 | 降级处理 | 对用户的影响 |
|---|---|---|
| 某平台 API 超时 | 继续用其他平台数据 | 报告显示"XX平台数据暂不可用" |
| 快手评论 API 403 | 跳过快手评论采集 | 评论信号仅含抖音/小红书 |
| 评论采集全部失败 | `commentInsight = null` | 评论区块不展示 |
| LLM 深度分析超时 | 用本地规则生成 fallback verdict | 报告质量下降但不报错 |
| LLM 选题生成失败 | 返回 0 个选题 | 前端展示「选题生成失败，请重试」 |
| LLM 评论总结失败 | `aiSummary = undefined` | 评论区块隐藏 AI 总结，仍展示词频 |
| 无低粉爆款候选 | `lowFollowerEvidence = []` | 报告显示「未发现低粉爆款，赛道已成熟」 |
| TikHub 账号限流 | 等待 retry（最多2次，间隔5s） | 采集延迟，不失败 |

## 附录：常见问题 FAQ

**Q：为什么过滤 30 天，不用 7 天或 90 天？**  
A：短视频赛道的热度生命周期通常是 3-6 周。7 天太短，会漏掉正在爬坡期（第 8-14 天）的新兴赛道；90 天会混入大量已经进入衰退期的历史赛道数据，导致预测出「已经过时的机会」。30 天覆盖一个完整的内容热度周期（爬坡 → 峰值 → 初期衰退），是捕捉「正在进行中」的机会的最优时间窗口。

**Q：1000 点赞的过滤门槛是怎么确定的？**  
A：低于 1000 赞意味着该内容停留在平台冷启动的第一流量池（约 200-500 播放量）没有突破，说明平台算法判断内容质量不达标，主动限制了分发。这类内容存在于搜索结果里，是因为它们在关键词上有匹配，但实际上是算法分发失败的内容，不能代表真实赛道需求。把它们纳入分析会降低低粉爆款算法的精度，因此在进入评分前过滤。

**Q：低粉爆款算法为什么粉丝上限是 10,000，不是 5,000 或 20,000？**  
A：10,000 粉是短视频平台「粉丝基本盘形成」的临界点。根据对抖音平台内容分发机制的研究，1 万粉账号的内容，来自粉丝的自然触达大约占总播放量的 15-25%，其余来自算法推荐。这个比例在可接受范围内，说明 1 万以下的高互动基本还是算法行为。超过 2 万粉的账号，粉丝贡献比例上升到 30-40%，算法信号被稀释，误判率上升。5,000 以下的样本量在很多赛道里太稀少，无法支撑算法得出稳定结论。10,000 是样本丰富度和信号纯度的平衡点。

**Q：P75 基准是实时计算的还是历史均值？**  
A：每次分析都**实时计算**，基于当次搜索到的所有有效内容的点赞数分布。这意味着不同赛道、不同时间点的 P75 值是不同的。比如美食赛道的 P75 可能是 5 万赞，小众手工艺赛道的 P75 可能只有 800 赞。用动态 P75 而不是历史均值，让算法能自适应不同体量赛道，不需要人工针对每个赛道设置阈值。

**Q：三维评分中，40/35/25 的权重是如何确定的？有没有科学依据？**  
A：权重设计基于「信号独立性和可信度」排序。粉丝效率比（40%）是最直接的「内容本身的传播力」证明，不依赖任何基准比较，置信度最高；P75 超越倍数（35%）提供了「相对于赛道的稀缺性」判断，但依赖当次搜索样本，有一定采样误差，权重次之；低粉程度（25%）是辅助维度，因为入口条件（< 10000 粉）已经做了预筛选，在此范围内做细分的增量价值相对较小。三个维度权重之和为 100%，使用的是加权线性组合，是机器学习领域常用的「特征加权融合」方法。

**Q：快手评论为什么不可用？**  
A：TikHub 的快手评论接口目前返回 403/500，是 API 供应商层面的限制，与我们的系统无关。快手搜索接口正常，因此快手内容数据（点赞、账号等）仍然可以纳入分析，只是缺少评论文本分析。未来 TikHub 支持快手评论接口后，可直接接入，无需修改我们的系统架构。

**Q：LLM 的输出是否可靠？如何保证一致性？**  
A：系统对 LLM 可靠性做了三层保障：① 输出格式约束：所有关键模块要求 LLM 返回 JSON 而非自然语言，便于校验；② 数值范围校验：分数维度（0-100）超界时自动截断；③ 低 temperature：意图识别 0.1、评分 0.2，确保同一输入多次调用的输出波动在 ±5% 以内。对于选题生成（temperature 0.4），我们允许更多变异性，因为这里的目标是「多样的创意建议」而非「确定性的数字判断」。

**Q：如果某个平台 API 全部失败，预测结果还有参考价值吗？**  
A：有，但置信度会下降，体现在 risk（风险度）分数上升。系统会标注「抖音数据暂不可用，仅基于小红书数据分析」。两个平台的数据相互独立，单平台数据已经足以支撑赛道机会判断，只是跨平台验证的置信度会降低。如果三个平台都失败（极端情况），系统会返回「数据采集失败，建议重试」，不会输出一个没有数据支撑的预测结果。
